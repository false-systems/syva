# Syva Observer design

Status: design only. This document specifies boundaries and implementation
preconditions; it does not add an Observer daemon.

## Purpose

Observer explains what Syva is protecting now, whether the protection can be
verified, and which meaningful workload/security changes have occurred. Syva
continues to make the kernel decision. Observer never becomes a policy
engine, SIEM, anomaly detector, packet capture system, secret scanner, or
remote authorization service.

## Chosen topology

Observer is a dedicated node-local daemon, `syva-observer`, with two optional
providers:

```text
                 optional read-only
           ┌────────────────────────┐
           │ Kubernetes provider    │
           │ pod/owner/spec context │
           └───────────┬────────────┘
                       │
┌──────────────┐  read-only local  ┌────────────────┐  optional export
│ syva-core    │◄──── Unix API ────►│ syva-observer  │────────► sinks/Vartio
│ enforcement  │  status/events    │ state/explain  │
└──────────────┘                   └────────────────┘
```

Decision: separate daemon.

Alternatives considered:

- **Subsystem in `syva-core`**: lowest IPC cost, rejected because it expands
  the privileged enforcement process and couples observation failure to core
  lifecycle.
- **Library only**: useful for tests and embedding, but insufficient as the
  default node-local continuity process. The implementation may expose a
  library crate underneath the daemon.
- **Cluster service**: rejected as the primary topology; it makes local
  explanation depend on a network/control plane and weakens standalone use.

Tradeoff: one additional daemon and local API surface in exchange for clear
privilege/failure isolation and testable standalone operation.

## Privilege and security boundary

Observer should run non-root where possible. It needs:

- read access to the Syva Unix socket;
- read-only `/proc`, cgroup, and mount metadata for local enrichment;
- optional read-only Kubernetes credentials with the smallest namespace/node
  RBAC needed;
- no `CAP_BPF`, `CAP_SYS_ADMIN`, BPF map write access, policy write access, or
  runtime socket write access.

If the core socket cannot provide a read-only credential boundary, add a
read-only Observer API or socket group rather than granting Observer core
write authority. A compromised Observer may lie to operators or exporters,
but must not be able to disable enforcement, mutate maps, load programs, or
activate generations.

## Evidence vocabulary

Every claim is tagged with:

- `kind`: `policy`, `kernel`, `observation`, or `inference`;
- `confidence`: `high`, `medium`, `low`, or `unknown`;
- `observed_at`: wall-clock time;
- `kernel_time_ns`: optional BPF monotonic timestamp;
- `fresh_until`: freshness deadline;
- `source`: `syva-core`, `procfs`, `cgroupfs`, `kubernetes`, or an external
  provider;
- `generation`: active/staging policy generation when known.

The words mean:

- **policy**: what an adapter requested;
- **kernel**: what Syva reports attached/active or what a hook decided;
- **observation**: what Observer found in procfs, cgroupfs, mounts, or the
  Kubernetes API;
- **inference**: a derived explanation whose inputs remain visible.

Policy alone never proves enforcement. A denied event proves one decision, not
that every future operation will be denied.

## Event model

Use a small versioned envelope rather than one message per source:

```text
ObservationEvent {
  schema: syva.observation.v1
  event_id: stable UUID/ULID generated by Observer
  sequence: local monotonic sequence; gaps are explicit
  observed_at: wall-clock timestamp
  kernel_time_ns: optional monotonic kernel time
  kind: workload|zone|enforcement|policy|posture|exposure
  subject: WorkloadRef or NodeRef
  decision: optional allow|deny|would_deny|escape
  claim_kind: policy|kernel|observation|inference
  confidence: high|medium|low|unknown
  active_generation: optional u64
  evidence_refs: bounded list
  gap: optional {from, to, reason}
}
```

Initial event kinds should be limited to:

- `workload.discovered`, `workload.removed`, `workload.identity_changed`;
- `zone.joined`, `zone.left`, `zone.changed`;
- `enforcement.state_changed`, `enforcement.hook_changed`;
- `policy.state_changed`;
- `operation.denied`, `operation.would_deny`, `operation.escape`;
- `posture.changed`, `observation.gap`.

Do not emit every allowed syscall. Allowed operations are summarized by
bounded counters; denial/escape events remain evidence. Event IDs are for
Observer's local stream and deduplication, not a claim of global ordering.

## State model

Observer maintains a bounded in-memory materialized view:

```text
NodeState
  core_status
  hook_states
  generation_state
  observer_freshness
  workloads: bounded map<WorkloadKey, WorkloadState>
  recent_events: bounded ring
  gaps: bounded list

WorkloadState
  stable identity
  optional Kubernetes identity
  cgroup identity and freshness
  zone and profile
  policy/enforcement evidence
  exposure assessments
  posture
  last relevant events
```

Default retention is memory-only with bounded recent events. Restart rebuilds
state from a core snapshot, current proc/cgroup observations, and optional
Kubernetes relist. Until that resync completes, affected state is `UNKNOWN`.
No SQLite/WAL is required for the first implementation. A future persistence
provider must preserve bounded disk use and explicit gaps; it must not become a
precondition for enforcement.

## Identity model

`WorkloadKey` is a tuple of source-qualified stable identity:

```text
source + runtime/container ID + optional pod UID
```

The cgroup ID is the current kernel attachment key, not the durable identity.
PID is only an observation-time handle. A cgroup ID change, container ID reuse,
pod UID change, or unresolved process must create an identity transition and
invalidate stale posture. Numeric cgroup reuse never silently updates an old
workload record.

## Posture model

Use semantic states, not a numeric score:

- `PROTECTED`: all mandatory invariants are satisfied with fresh evidence;
- `DEGRADED`: Syva is enforcing some policy, but an optional or required
  posture property is weakened or evidence is stale;
- `EXPOSED`: a known unsafe configuration or observed reachable authority is
  present;
- `UNKNOWN`: required evidence is missing, contradictory, or too old.

`PROTECTED` requires, at minimum:

1. core reports active enforcement, not disabled/unsafe;
2. every expected hook is attached and self-tests are passed;
3. active policy generation is known and no staging mismatch is pending;
4. workload identity and zone membership are fresh and unambiguous;
5. mandatory profile requirements, if any, are satisfied by explicit evidence;
6. no known unsafe Kubernetes/runtime configuration is present;
7. Observer freshness is within its configured bound.

Missing evidence produces `UNKNOWN`, not `PROTECTED`.

## Agent profile assessment

Observer reports each requirement as `satisfied`, `violated`, `unknown`, or
`not_supported`, with evidence and enforcement class:

| Requirement | Syva today | Observer responsibility |
|---|---|---|
| Cross-zone ptrace/signals | enforceable | verify policy + kernel denial evidence |
| Cross-zone Unix/process access | enforceable | verify policy + events |
| Protected registered host files / exec / mmap | enforceable | verify policy/map state + events |
| Network-locked egress/CIDR | enforceable for supported hooks | verify mode, map state, and decisions |
| Kubernetes membership/cgroup coverage | partially enforceable via adapter | correlate identity and freshness |
| Service-account token mount | not enforced by Syva | inspect pod volume/mount metadata |
| Docker/containerd/CRI socket exposure | filesystem enforcement possible when registered; not automatic | identify socket by inode/mount/runtime evidence |
| privileged, hostPID, hostIPC, hostNetwork | not enforced by Syva | report Kubernetes configuration as exposure |
| hostPath risk | policy-dependent; not a generic safe-hostPath proof | classify mount source/path and uncertainty |
| cloud metadata reachability | network policy may block supported destinations | assess configured paths and optional active probe; never infer reachability from policy alone |
| arbitrary credentials/secret contents | not supported | report only known authority mounts, never scan contents |
| unrestricted outbound network | not blocked in bridged/host mode | report `EXPOSED` or profile violation |

The profile is explicit data, not magic defaults. A future `profile: agent`
must enumerate requirements and allow operators to see which are unsupported.

## Metadata service semantics

All providers share a destination catalog with family, endpoint, port, and
provider metadata. It is not a single IPv4 constant.

- AWS IMDS: IPv4 `169.254.169.254`, optional IPv6 `[fd00:ec2::254]`; IMDSv2
  requires a token and the IPv6 endpoint is separately enabled on Nitro/IPv6
  configurations. See [AWS IMDS options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html).
- GCP metadata: `169.254.169.254`, `metadata.google.internal`, and IPv6
  `fd20:ce::254` for IPv6-only instances; requests require the
  `Metadata-Flavor: Google` header. See [GCP metadata overview](https://docs.cloud.google.com/compute/docs/metadata/overview).
- Azure IMDS: `169.254.169.254` under `/metadata`, requiring the `Metadata:
  true` header and a mandatory API version. See [Azure IMDS](https://learn.microsoft.com/en-us/azure/virtual-machines/instance-metadata-service).

Observer classifies a metadata target as `blocked`, `allowed_by_policy`,
`reachable_observed`, `unreachable_observed`, or `unknown`. A policy entry is
not proof of route reachability. Host networking, proxies, CNI routing,
IPv6-only paths, and provider-specific headers remain explicit uncertainty.

## Runtime sockets and credentials

Do not scan a fixed path list and call that protection. Discover candidate
Unix sockets from mount/source metadata, runtime configuration, known socket
names, and inode identity; then correlate with Syva's inode and Unix-socket
policy evidence. Candidate paths include Docker, containerd, and CRI-O socket
locations, but paths are evidence, not identity.

Credential exposure is authority exposure only: projected Kubernetes service
account token mounts, SSH-agent sockets, cloud credential mount paths, and
runtime control sockets. Observer does not read token or credential contents.

## Local API and CLI

Reuse the existing Syva Unix-socket/protobuf conventions. Add a read-only
versioned Observer API only after the core snapshot seam is defined:

```text
GetObserverStatus
GetWorkloadStatus
ListWorkloads
WatchObservations
ExplainObservation
GetPosture
```

The initial CLI should expose only:

```text
syvactl status                 # preserve existing core status
syvactl observe                # bounded live observation stream
syvactl posture <workload>     # semantic posture + evidence
syvactl explain <event-id>    # one event and its evidence chain
```

Do not add a second network service or a generic query language. Existing
`syvactl events --follow` remains the raw Syva event view.

## Kubernetes enrichment

Kubernetes is an optional provider. It maps pod UID, namespace/name, owner,
labels, service account, security context, host namespace flags, volumes, and
node identity onto the kernel-backed WorkloadKey. Kubernetes metadata never
overrides cgroup or kernel evidence. API loss marks affected enrichment stale
and can move posture to `UNKNOWN`; it does not stop core enforcement.

## Optional Vartio evidence export

Vartio is an asynchronous context/evidence consumer, never a syscall decision
dependency. Observer may export a versioned `syva.observation.v1` envelope with
stable workload/event IDs, policy generation, decision, evidence provenance,
confidence, and explicit gaps. Export uses a bounded queue, retry/backpressure,
and drop accounting. If Vartio is unavailable, Observer continues locally and
marks export gaps; Syva continues enforcing.

No direct Ahti or Vartio dependency is introduced in the first Observer stage.

## Failure semantics

| Failure | Syva enforcement | Observer state |
|---|---|---|
| Observer crash | unchanged | state lost; `UNKNOWN` until resync |
| Syva core restart | pinned generation remains per core contract | resync; mark unknown during transition |
| BPF maps/programs disappear | core health becomes unsafe/degraded | `EXPOSED`/`UNKNOWN` based on core evidence |
| Kubernetes API unavailable | unchanged | Kubernetes fields stale; no false protection |
| Vartio unavailable | unchanged | export gap only |
| event subscriber lag/drop | unchanged | explicit sequence gap; no complete-history claim |
| malformed provider data | unchanged | reject record; retain prior state only until freshness expires |

## Performance and boundedness

- no Observer code runs inside BPF-LSM hooks;
- no synchronous network call is made by core or an event decision;
- kernel events remain small; userspace performs enrichment;
- event queue, recent history, provider caches, and export queue are bounded;
- state reconciliation is event-assisted with periodic full resync;
- allowed operations are counters, not per-operation events;
- performance thresholds are measured in the implementation stage rather than
  invented here.

## Alternatives and tradeoffs

- **Core-integrated Observer**: lower latency, unacceptable privilege and
  failure coupling.
- **Kubernetes-only controller**: rich metadata, violates standalone use.
- **Full event database**: durable history, violates bounded/lean scope.
- **Remote Vartio authority**: richer context, violates deterministic local
  enforcement.
- **Active network probing by default**: stronger reachability evidence,
  risks side effects and false confidence; make probes explicit and optional.
